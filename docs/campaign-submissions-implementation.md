# 챌린지 게시물 제출·운영 구현

2026-09-07 기준 구현을 완료했으며 운영 DB 적용과 프로덕션 배포는 아직 수행하지 않았다.
설계는 `docs/design-campaign-submissions.md`를 따른다.

## 제공 기능

- 운영자는 기존 `/tools/campaigns/[projectId]?tab=submissions`에서 확정 참여자 전체를 표로 관리한다.
- 상태·담당자·기한 필터, 이름·계정 검색, 명단·제출 안내 문구 복사, 50행 페이지 이동을 제공한다.
- 관리자는 참여자 행에서 게시물 링크를 대신 등록하고, 수정 요청·확인 완료를 처리한다.
- 회원은 `/applications`에서 진입해 `/campaigns/[projectId]/submit`에서 링크와 검토 결과를 확인하고 수정·재제출한다.
- 직접 섭외한 보드 참여자는 지원서 없이도 등록할 수 있으며 담당자가 회원 연결 근거를 기록하면 본인 제출을 사용할 수 있다.
- 별도 등록된 미연결 게시물은 확정 참여자에게 연결할 수 있다.
- 공개 설정이 켜진 캐스팅 보드에는 승인된 링크의 배지와 업로드 현황 보기가 나타난다.
- 발행 보고서에는 승인된 현재 링크와 제출 현황을 동결하며, 제출 기능을 꺼도 미검토 게시물이 노출되지 않는다.
- 링크 교체, 같은 URL의 캡션 수정 후 재검토, 공동작업, 이탈과 개별 기한 변경의 이력을 보존한다.

## 데이터·권한

마이그레이션 파일은 `db/migrations/20260907133055_campaign_submissions.sql`이다.
신규 테이블 네 개는 모두 RLS 활성·공개 정책 없음·service-role 전용이다.

- `campaign_submission_settings`: 제출 활성화, 명단 기준 보드, 기본 마감, 공개 설정과 버전.
- `campaign_participants`: 확정 참여자 원장, 지원서·보드·댄서 연결, 담당자·기한·이탈 여부.
- `campaign_submissions`: 게시물 연결, 검토 상태, 수정 사유, 버전과 교체 이력.
- `campaign_submission_events`: 처리자와 변경 전 상태를 보존하는 감사 기록.

기존 `campaign_posts`가 URL·성과 지표의 정본이다.
공동작업 게시물을 여러 참여자에게 연결해도 게시물·조회수는 한 번만 집계한다.
RPC는 SECURITY INVOKER이며 anon·authenticated에는 실행 권한을 주지 않는다.
서버에서 검증된 사용자 ID를 전달하고 RPC에서도 담당 프로젝트·본인 소유·현재 확정 상태를 확인한다.
프로젝트 행 잠금과 버전 비교로 동시 수정 충돌을 차단한다.
게시물·참여자 복합 외래키와 참여자 범위 트리거가 프로젝트 간 잘못된 연결을 거부한다.

## 검증

- `npm run test:campaigns`: 기존 성과 회귀와 신규 제출 테스트 48건 통과.
- 신규 SQL은 실제 마이그레이션을 PGlite PostgreSQL에 적용하고 service_role 권한으로 검증했다.
- 로컬 Next.js와 격리된 Auth·REST 어댑터를 연결해 실제 서버 액션을 실행했다.
- 브라우저에서 미제출 필터, 관리자 대신 등록, 검토 체크 필수, 승인, 수정 요청, 본인 재제출, 타인 404, 로그인 복귀, 공개 미리보기의 승인 링크 한정, 모바일 가로 넘침을 검증했다.
- 전역 Playwright를 사용하며 실행 명령은 PowerShell에서 `$env:NODE_PATH = (npm root -g); node scripts/campaign-submissions-browser.cjs`다.
- 시각 증빙과 실행 결과는 `C:/Users/tkay/Desktop/deliverables/deetz-campaign-submissions-20260907/`에 있다.
- 최종 린트·타입 검사·프로덕션 빌드 결과는 PR에 기록한다.

브라우저 검증의 인증·REST 계층은 로컬 테스트 어댑터다.

## 운영 반영 순서

1. 프로덕션 반영 승인을 받은 뒤 최종 마이그레이션 파일을 운영 DB에 적용한다.
2. 검증된 PR을 병합하고 deetz 운영 배포 완료를 확인한다.
3. 초기 등록 파일로 최신 확정 명단과 두 링크를 등록하고 상태별 건수를 확인한다.
4. 관리자·본인 권한과 기존 보드·보고서의 정상 표시를 확인한다.
5. 실제 게시물을 검토한 뒤 확인 완료로 처리하고 클라이언트 보드 공개 여부를 설정한다.

이번 구현은 이메일·채팅 발송, Apify 측정, 대외비 공지 복구를 실행하지 않는다.
일반 캠페인에서 명단 기준 보드를 정하지 않으면 최종 확정 지원서만 가져온다.
명단 동기화는 새 참여자 추가만 수행하며, 기존 참여자의 이탈은 운영자가 별도로 처리한다.
장애 시 이전 앱 배포로 되돌리고 신규 데이터를 보존한다.
신규 테이블 삭제를 롤백 절차로 사용하지 않는다.
