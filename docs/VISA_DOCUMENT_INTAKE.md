# 비자 서류 정보 제출 페이지 기획·구현 정본

작성일은 2026-08-28이다.

현재 상태는 운영 DB 마이그레이션, deetz·grigoent 배포, 기존 결제 주문 대사와 운영 E2E까지 완료한 라이브 상태다.

## 목표

비자 프로그램 또는 GRIGO 트레이닝 프로그램 결제를 완료한 외국인 회원이 비자 서류 작업에 필요한 정보를 직접 제출한다.

여권 사본, 개인 댄서 프로필, 증명사진과 주요 활동 실적 사진도 같은 페이지에서 직접 첨부한다.

긴 폼 작성 중 이탈하거나 브라우저 오류가 발생해도 입력 손실을 최소화한다.

기존 회원·신청·결제·국적 데이터를 복제하지 않고 자동 입력 가능한 값은 기존 정본에서 읽는다.

여권번호와 국가식별번호는 일반 JSON 데이터와 분리해 애플리케이션 계층에서 AES-256-GCM으로 암호화한다.

## 사용자 진입 조건

회원은 로그인 상태여야 한다.

회원 본인의 `dancer_visa_applications.applicant_profile_id`와 연결된 결제 완료 케이스가 있어야 한다.

비자 신청으로 시작한 회원은 기존 구조화 국적 판정과 이메일 완전 일치 연결 규칙을 그대로 사용한다.

GRIGO 프로그램에서 바로 결제한 회원은 결제 콜백이 deetz 케이스를 생성하거나 같은 이메일의 기존 케이스에 연결한다.

운영 대상 프로그램 slug는 `training-and-placement`, `monthly-training`, `monthly-training-100`이다.

기존 미연결 결제 완료 주문은 결제 복구 cron이 한 번에 20건씩 멱등 연결한다.

## 화면 구성

페이지 경로는 `/me/visa/documents`다.

페이지는 여덟 단계로 나뉜다.

1단계는 기본 인적사항이다.

2단계는 국적·주여권·다른 유효 여권·과거 사용 성명이다.

3단계는 한국 체류 중 비상 연락처다.

4단계는 최종 학력과 학교 소재지다.

5단계는 혼인·배우자·자녀·한국 거주 가족·동반 가족이다.

6단계는 최근 5년간 한국 방문 횟수와 가장 최근 방문 기록이다.

7단계는 최근 5년간 한국 외 국가 방문 기록이다.

8단계는 첨부자료, 민감정보 수집 동의와 최종 제출이다.

한국어·영어·일본어 UI를 모두 제공한다.

기존 `dancer_visa_applications.preferred_lang`을 최초 표시 언어와 언어 변경 자동저장의 정본으로 재사용한다.

## 필수 조건

한자 성명은 DB 필수값이 아니다.

일본·중국 등 한자권 신청자는 제출이 필요하다는 안내 문구를 표시한다.

자택 전화가 없으면 `없음`을 선택할 수 있다.

현재 거주지는 본국 주소와 다른 경우에만 입력한다.

복수 국적·다른 여권·과거 다른 성명·배우자·자녀·한국 가족·동반 가족은 조건부로 펼친다.

여행 기간은 시작일과 종료일을 날짜 단위로 받는다.

종료일이 시작일보다 빠르면 제출을 막는다.

국가식별번호를 발급받지 않은 경우 `해당 없음`을 선택할 수 있다.

일본 국적자는 일본 My Number를 이 페이지에서 수집하지 않는다.

일본 국적 판정은 클라이언트 비활성화와 서버 저장 차단을 모두 적용한다.

첨부자료는 여권 사본 1개, 개인 댄서 프로필 1개, 증명사진 1개와 주요 활동 실적 사진 최소 4개가 필수다.

활동 실적 사진은 4개를 넘겨 추가할 수 있으며 애플리케이션 차원의 개수 상한을 두지 않는다.

여권 사본과 개인 댄서 프로필은 PDF 또는 이미지로 받는다.

증명사진과 활동 실적 사진은 이미지만 받는다.

지원 형식은 JPG, PNG, WEBP, HEIC, HEIF와 해당 문서의 PDF다.

bucket의 개별 파일 크기 제한은 두지 않고 Supabase 프로젝트 전역 Storage 한도만 최종 인프라 가드로 적용한다.

6MB를 넘는 파일은 6MB chunk의 TUS 재개형 업로드를 사용해 네트워크가 끊겨도 이어서 전송한다.

6MB를 넘는 JPG, PNG, WEBP는 최대 변 4096px와 고화질 JPEG 기준으로 브라우저에서 자동 최적화하되 결과가 원본보다 작을 때만 최적화본을 업로드한다.

브라우저 호환상 직접 최적화하기 어려운 HEIC, HEIF와 PDF는 원본을 재개형 업로드한다.

증명사진 안내는 35×45mm, 흰색 바탕, 모자 미착용, 정면 촬영, 최근 6개월 이내, 여권사진과 다른 사진이라는 조건을 그대로 표시한다.

## 임시저장 정책

입력 변경 후 1.2초가 지나면 백그라운드 저장한다.

필드에서 포커스가 빠질 때 저장을 시도한다.

다음 단계나 이전 단계로 이동하기 전에 저장을 시도한다.

작성 중에는 15초마다 저장을 재확인한다.

탭이 숨겨지거나 페이지가 내려갈 때 최선 노력 방식으로 저장을 시도한다.

성공할 때마다 토스트를 띄우지 않는다.

상단에 `Saving`, `Saved`, `Save failed`, `Reload required` 상태만 작게 표시한다.

`draft_version`을 비교하는 낙관적 잠금으로 다른 탭의 최신 저장을 덮어쓰지 않는다.

충돌하면 자동 병합하지 않고 새로고침을 요구한다.

민감정보는 `localStorage`, 로그, 분석 이벤트, 이메일에 저장하지 않는다.

파일은 선택한 건마다 즉시 업로드하고 업로드가 완료된 뒤에만 첨부 원장에 기록한다.

업로드 완료 파일은 새로고침과 재접속 후에도 복구하며 개별 열람, 교체와 삭제를 제공한다.

활동 사진은 여러 장을 한 번에 선택할 수 있고 각 업로드 상태를 파일 슬롯별로 표시한다.

## DB 설계

`visa_document_intakes.application_id`는 `dancer_visa_applications.id`를 참조하는 기본키다.

신청 한 건당 초안 한 건만 존재한다.

`form_data`에는 여권번호와 국가식별번호를 제외한 구조화 데이터만 저장한다.

`sensitive_data_ciphertext`에는 국가식별번호와 주여권·추가여권 번호의 암호문만 저장한다.

`draft_version`은 비교 후 갱신 방식의 동시성 제어에 사용한다.

상태는 `draft`, `submitted`, `needs_revision`, `accepted`만 허용한다.

RLS를 활성화하고 `anon`, `authenticated` 권한을 회수한다.

회원 요청은 서버 액션이 사용자와 결제 완료 케이스를 검증한 뒤 service role로 처리한다.

`dancer_visa_applications.external_training_order_id`는 미연결 프로그램 주문의 중복 케이스 생성을 막는 부분 유니크 키다.

`email_normalized`는 기존 이메일을 바꾸지 않고 정확한 소문자 비교를 위한 생성 컬럼이다.

`visa_document_attachments`는 신청 ID, 자료 종류, 0부터 시작하는 슬롯, 비공개 Storage 경로, 원본 파일명, MIME, 크기와 업로드 사용자를 기록한다.

단일 문서는 종류당 슬롯 0 한 개만 허용하고 활동 사진은 0 이상의 정렬 순서를 사용해 4개 이후에도 계속 추가할 수 있다.

기존 정산 서류용 `dancer-docs`는 프로필 단위 권한이므로 재사용하지 않는다.

비자 신청 단위 전용 비공개 버킷 `visa-documents`를 사용하며 회원은 `storage.objects`에 직접 접근할 권한이 없다.

서버가 본인의 결제 완료 신청인지 확인한 뒤 고유 경로의 signed upload token을 발급하고 브라우저는 해당 경로 한 건만 업로드한다.

업로드 완료 액션은 Storage의 실제 객체 MIME과 크기를 다시 확인한 뒤 메타데이터를 저장한다.

회원과 관리자의 열람은 짧은 만료시간이 있는 signed URL로만 제공한다.

## 암호화와 키 관리

암호화 방식은 AES-256-GCM이다.

각 저장은 새로운 12바이트 IV를 사용한다.

애플리케이션 ID와 암호문 버전을 AAD에 포함한다.

전용 `VISA_DOCUMENT_ENCRYPTION_KEY`가 있으면 우선 사용한다.

전용 키가 없으면 기존 양 앱 공유 비밀 `VISA_PAYMENT_LINK_SECRET`에서 HKDF로 별도 키를 파생한다.

전용 키는 production·preview 환경에 등록한다.

암호화 키를 교체하려면 기존 암호문 재암호화 절차와 버전 마이그레이션이 필요하다.

## 결제 동기화

grigoent는 결제 정본을 계속 소유한다.

결제가 완납되면 서명된 `program_enrollment` 콜백을 deetz로 보낸다.

콜백은 외부 주문 ID를 먼저 조회하고 같은 요청의 재전송을 조용히 성공 처리한다.

외부 주문 ID가 없으면 정규화 이메일로 기존 케이스를 찾는다.

기존 케이스가 있으면 결제 사실과 외부 주문 연결만 갱신하고 기존 단계·메모·신청 경로를 덮어쓰지 않는다.

기존 케이스가 없으면 최소 프로그램 케이스를 만든다.

deetz가 반환한 케이스 ID는 `training_orders.visa_application_id`에 기록한다.

콜백 실패가 이미 성공한 결제 결과를 사용자에게 실패로 보이게 하지는 않는다.

결제 복구 cron이 미연결 완료 주문을 다시 대사한다.

## 테스트와 출시 게이트

스키마 단위 테스트는 민감번호가 `form_data`에 포함되지 않는지 확인한다.

스키마 단위 테스트는 불완전 초안 허용과 최종 제출 필수 검증을 분리해 확인한다.

브라우저 E2E는 자동저장, 단계 이동, 일본 국적 차단, 여행 반복행, 제출, 모바일 넘침을 확인한다.

첨부 E2E는 필수 7개 파일 업로드, 4개 초과 활동 사진 추가, 대용량 사진 자동 최적화, TUS 업로드 진행률, 교체·삭제, 새로고침 복구, 제출 잠금, 관리자 열람과 비공개 URL 차단을 확인한다.

deetz 타입검사·대상 ESLint·프로덕션 빌드가 통과해야 한다.

grigoent 프로덕션 빌드가 통과해야 한다.

운영 출시 순서는 deetz DB 마이그레이션, deetz 배포, grigoent 배포, 미연결 주문 대사 확인 순이다.

배포 후에는 실제 테스트 계정으로 임시저장 재접속, 다른 탭 충돌, 제출 후 운영 DB 암호문, 로그 내 민감정보 부재를 확인한다.

관리자는 `/admin/visa/[application_id]/documents`에서 제출 상태와 복호화된 서류 내용을 서버 측에서만 열람한다.

관리자 페이지는 동적 렌더링하고 비관리자에게는 노출하지 않는다.

일괄 내보내기는 제공하지 않으며 관리자는 필요한 첨부 파일만 만료형 signed URL로 개별 열람한다.
