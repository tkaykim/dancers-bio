# deetz 퀄리티 관리 설계 — 승인 기준 + 댄서 종합평점(DQS)

> 2026-08-14 초안.
> 목적: ① 승인/거절의 판단 기준을 규칙으로 고정한다 ② 프로젝트별 현장 평가가 누적되는 종합평점을 만들어 플랫폼 퀄리티를 관리한다.
> 근거 데이터는 전부 운영 DB(`wvfmqiajdvbsevlhlgtl`) 실조회(2026-08-14).

**해석**: 평가 인프라의 절반은 이미 깔려 있다.
`application_evaluations`(사전선별 점수)와 `event_participants`(출석·노쇼·현장상태)가 이미 데이터를 쌓고 있어서, 새 시스템을 맨바닥에서 만들 필요가 없다.
비어 있는 것은 **"프로젝트가 끝난 뒤의 평가"** 한 조각뿐이다.

## 1. 설계 원칙

1. **승인 게이트는 낮게, 품질 관리는 점수로.**
   승인을 까다롭게 해서 775명을 걸러내는 방식은 공급이 줄고 운영 부담만 커진다.
   승인은 "명단에 올릴 최소 자격"만 보고, 실제 퀄리티 관리는 추천·정렬 점수(DQS)로 한다.
2. **점수는 절대 공개하지 않는다.**
   기존 `dancer_scores` 설계 원칙(admin-only RLS, RPC가 내부 정렬만 수행)을 그대로 승계한다.
   댄서가 자기 등급을 보면 플랫폼은 즉시 분쟁·어뷰징 무대가 된다.
3. **자동은 추천까지, 결정은 사람이.**
   자동 차단·자동 블랙리스트는 만들지 않는다.
   낮은 점수는 "관리자 확인 큐"로 보내고 사람이 판단한다.
4. **표본이 적으면 판단하지 않는다.**
   평가 1~2건으로 등급을 매기지 않고 중립값으로 수축(shrinkage)시킨다.
5. **모든 평가는 근거와 함께 남는다.**
   누가·언제·어떤 프로젝트에서 매겼는지 추적 가능해야 이의제기에 답할 수 있다.

## 2. Part A — 승인 기준

### 2-1. 승인의 의미 재정의

현재 `approval_status`가 실제로 바꾸는 것은 **명단 노출**이다.
공개 프로필 URL은 승인과 무관하게 열린다(`get_public_dancer`, 2026-06-27 의도적 설계 — 단건 조회는 허용, 명단 덤프만 차단).
따라서 승인 기준 질문은 "이 사람을 공개할까"가 아니라 **"이 사람을 deetz 명단·검색·캐스팅 추천에 올려도 되는가"** 이다.

### 2-2. 4단계 트리아지 (자동 분류 → 사람 확인)

| 등급 | 조건 | 조치 | 실측 인원 |
|---|---|---|---|
| **A — 자동 승인 후보** | 사진 O + 장르 O + (경력 ≥1 **또는** `is_verified`) | 일괄 승인 | **218명** (동명 충돌 49명 빼면 기본 선택 **169명**) |
| **B — 보완 요청** | 사진 O + 장르 O + 경력 0 | pending 유지 + 보완 안내 → 14일 후 재판정 | **362명** |
| **C — 정보 부족** | 활동명·사진·장르 중 누락 | 보완 안내(가입자) / IG 재수집(큐레이션) | **172명** |
| **REVIEW — 연락처 중복** | 다른 프로필과 연락처 완전 일치 | 병합 여부 결정 후 개별 승인 | **26명** |
| **D — 거절** | 사칭·무관인물·본인 요청 | `rejected` + 사유 기록 | 개별 판정 |

**하드 게이트(무조건 승인 불가)**: 활동명 없음, 사진 없음, 장르 없음.

⚠️ **SNS 링크 보유는 실재성 근거로 쓰지 않는다.**
pending 778명 중 743명이 SNS 링크를 갖고 있어 게이트 역할을 전혀 못 한다.
실재성은 **경력 1건 이상** 또는 **관리자 검증(`is_verified`)** 으로만 인정한다.

**거절은 좁게 쓴다.**
현재 rejected가 1건뿐인 것은 운영이 옳게 흘러온 것이다.
"미달"은 거절이 아니라 pending 유지 + 보완 요청이며, rejected는 **되돌릴 이유가 없는 경우**(사칭·중복·본인 요청)에만 쓴다.

### 2-3. 승인 전 필수 체크: 중복계정 — 신호 강도를 나눈다

중복을 승인하면 명단·추천·정산이 전부 갈라지므로 트리아지에 중복 탐지를 먼저 건다.
다만 **활동명 일치와 연락처 일치는 신뢰도가 완전히 다르다**(실측으로 확인).

| 신호 | 인원 | 실제 내용 | 처리 |
|---|---|---|---|
| **강함 — 연락처 완전 일치** | 26명 | 표본 확인 결과 사실상 전부 진짜 중복 (같은 번호 + 같은 활동명) | REVIEW로 격리, **승인 차단** |
| **약함 — 활동명만 일치** | 91명 | "채원" 5건, "Minseo" 4건 등 **동명이인이 다수** | 등급 유지 + 배지 표시, 일괄 승인 **기본 선택에서만 제외** |

활동명 일치를 승인 차단으로 쓰면 동명이인 91명이 수동 큐에 갇힌다.
반대로 무시하면 "Anna Winchester" 3건 같은 진짜 중복이 통과한다.
그래서 **차단이 아니라 기본값 해제**로 처리해, 관리자가 눈으로 보고 켜도록 했다.

관련: [[reference_deetz_duplicate_dancer_accounts]]

### 2-4. 승인 후에도 되돌릴 수 있게

승인은 영구 훈장이 아니다.
DQS가 하위권으로 굳어지거나 노쇼가 누적되면 `display_order` 하향 → 추천 제외 → (심각 시) `is_active=false` 순으로 강등한다.
`approval_status`를 다시 pending으로 돌리지 않는다(사용자에게 "승인 취소"로 읽혀 분쟁이 된다).

## 3. Part B — 종합평점 DQS (deetz Quality Score)

### 3-1. 구조 (0~100점, 내부 전용)

```
DQS = P(프로필 20) + C(경력 30) + R(현장 신뢰도 50)
```

| 축 | 배점 | 출처 | 지금 가능? |
|---|---|---|---|
| **P** 프로필 완성도 | 20 | `dancers` 컬럼 자동 계산 | ✅ 즉시 |
| **C** 경력·시장가치 | 30 | 기존 `dancer_scores` 정규화 | ✅ 즉시 |
| **R** 현장 신뢰도 | 50 | 프로젝트별 평가 + 행동 로그 | 🟡 평가 수집 필요 |

현장 신뢰도에 절반을 준 이유는, 대표님이 관리하려는 퀄리티가 결국 **"다시 부를 수 있는 사람인가"** 이기 때문이다.
프로필과 경력은 진입 자격이고, 재섭외 가능성이 플랫폼의 진짜 자산이다.

### 3-2. P — 프로필 완성도 (20점, 전부 자동)

| 항목 | 점수 |
|---|---|
| 프로필 사진 | 4 |
| 장르 1개 이상 | 2 |
| 소개글 20자 이상 | 2 |
| SNS 링크 1개 이상 | 2 |
| 경력 3건 이상 | 4 |
| 영상 링크 있는 경력 1건 이상 | 3 |
| 연락처(폰) 등록 | 3 |

대표 영상이 있는 프로필과 없는 프로필의 캐스팅 전환율 차이가 크므로 영상에 가중을 준다.
이 점수는 **댄서 본인에게 공개해도 되는 유일한 점수**다(성장 피드백 용도).

### 3-3. C — 경력 (30점)

기존 `dancer_scores.score`(현재 상위 300점대, 로그성 분포)를 **백분위 → 30점 스케일**로 변환한다.
산식은 이미 `src/lib/scoring/career-score.ts`에 단일 소스로 있으므로 재사용하고, 변환 레이어만 추가한다.

### 3-4. R — 현장 신뢰도 (50점)

**R = 사람 평가 35 + 행동 로그 15**

#### (a) 평가 주체 3종 — 각자 "볼 수 있는 것만" 평가한다

한 사람이 모든 걸 평가하게 하면 안 된다.
디렉터는 댄서가 몇 시에 왔는지 모르고, 현장 매니저는 안무 완성도를 판단할 위치가 아니며, 클라이언트는 개별 댄서를 다 구분하지 못한다.
그래서 **주체별로 질문 자체를 다르게** 준다.

| 주체 | 누구 | 축 (5점 척도) | R 내 가중 |
|---|---|---|---|
| **현장 매니저** | deetz·GRIGO 운영자 (`event_staff`) | 시간 준수 / 소통 응답 / 현장 매너 / 지시 이행 / 서류·정산 협조 | **45%** |
| **디렉터** | 안무감독·프로젝트 담당 (`project_managers`) | 실력·습득 / 디렉션 수용 / 완성도 / 팀워크 | **40%** |
| **클라이언트** | 외부 발주사 (로그인 없음, 서명 토큰) | 전반 만족 **2문항만** | **15%** |

현장 매니저에 가장 큰 가중을 준 이유는, 매니저가 **전 프로젝트에 같은 기준으로 반복 등장**하는 유일한 관찰자이기 때문이다.
디렉터는 프로젝트마다 바뀌고, 클라이언트는 한 번 보고 만다.

**표본이 없는 주체는 가중치에서 빼고 나머지로 재정규화한다.**
클라이언트 평가가 없다고 그 15%가 0점으로 깎이면 안 된다.

**+ 재섭외 의향 (예/아니오) — 세 주체 모두에게 묻는다.**
축 평균은 평가자마다 후하거나 박해서 흔들리지만, "다시 부를 것인가"는 흔들리지 않는다.
재섭외 의향률을 R의 핵심 보정값으로 쓴다(의향률 100% → 가점, 50% 이하 → 감점).

**클라이언트 평가는 반드시 2문항으로 끝낸다.**
외부인에게 4축을 물으면 응답률이 무너진다.
이미 `/cast` 클라이언트 리뷰 토큰 인프라(`casting_boards.review_token_version`)가 있으므로 같은 링크에 얹는다.

#### (b) 행동 로그 — 전부 자동, 이미 쌓이는 데이터

| 신호 | 처리 | 원천 |
|---|---|---|
| 노쇼 | 큰 감점 (건당) | `event_participants.attendance_status='no_show'` |
| 수락 후 자진 이탈 | 감점 | `self_withdrawn` / `applications.status='withdrawn'` |
| 지각 | 소감점 | `checked_in_at` vs `project_schedules.starts_at` |
| 일정 응답률 | 가점/감점 | `project_schedule_responses` |
| 정산 정보 제출 지연 | 소감점 | `settlements` + `dancer_private_info` |

현재 노쇼는 4명 6건뿐이라 감점 대상은 극소수다.
즉 이 지표는 벌주기용이 아니라 **성실한 다수를 위로 올리는 용도**로 작동한다.

### 3-5. 통계 보정 (여기가 시스템의 신뢰도를 결정한다)

1. **표본 수축(Bayesian shrinkage)**
   `R_final = (n × R_관측 + k × R_평균) / (n + k)`, k = 3.
   평가 1건짜리 댄서가 만점/0점으로 튀는 것을 막는다.
2. **시간 감쇠**
   반감기 12개월 (`w = 0.5^(개월/12)`).
   3년 전 한 번의 실수가 영구 낙인이 되지 않게 한다.
3. **평가자 캘리브레이션**
   평가 5건 이상 쌓인 평가자는 본인 평균·분산으로 z-정규화 후 재스케일.
   "항상 5점 주는 디렉터"와 "최고가 4점인 디렉터"를 같은 자로 만든다.
4. **최소 표본 게이트**
   n < 2면 등급 라벨을 부여하지 않고 "평가 부족"으로 표시한다.

### 3-6. 등급 라벨 (내부 표시용)

절대 점수가 아니라 **백분위**로 매긴다.
S(상위 5%) / A(20%) / B(50%) / C(80%) / D(하위 20%).
절대 점수는 산식을 바꿀 때마다 등급이 요동치지만, 백분위는 안정적이다.

### 3-7. 평가 수집 UX — 회수율이 전부다

가장 잘 만든 산식도 평가가 안 걷히면 죽는다.

- **시점**: 프로젝트 마지막 일정 종료 다음 날.
- **대상**: 프로젝트 담당자(owner + `project_managers`).
- **형태**: 참여자 그리드 한 화면 — 행=댄서, 열=4축 별점 + 재섭외 토글.
  기본값은 "무응답"이며, **재섭외 토글만 눌러도 유효 데이터로 인정**한다(30초 컷).
- **리마인드**: 인앱 + 알림톡(신규 템플릿 필요) 1회, 7일 후 1회.
- **소프트 게이트**: 정산 확정 화면에서 미평가 참여자가 있으면 배너로 유도한다.
  하드 게이트(평가 안 하면 정산 못 함)는 정산이 급한 현장에서 반발이 크므로 쓰지 않는다.

### 3-8. 데이터 모델

기존 테이블을 최대한 재사용한다.

```sql
-- ① 현장 평가: application_evaluations 재사용 (stage 컬럼이 이미 확장 포인트)
--    stage = 'prescreen'(기존) | 'wrap'(신규, 종료 후 평가)
alter table application_evaluations
  add column if not exists axes jsonb,          -- {direction:5, manner:4, skill:4, pro:5}
  add column if not exists would_rebook boolean;

-- ② 종합점수 캐시 (admin-only RLS, dancer_scores와 동일 정책)
create table dancer_quality_scores (
  dancer_id uuid primary key references dancers(id) on delete cascade,
  dqs numeric not null default 0,
  profile_score numeric, career_score numeric, reliability_score numeric,
  eval_count int not null default 0,
  rebook_rate numeric,
  percentile numeric, grade text,
  breakdown jsonb,
  computed_at timestamptz not null default now()
);
```

`application_evaluations`의 `score`(1~10)는 사전선별용으로 유지하고, 종료 평가는 `axes` + `would_rebook`을 채운다.
같은 테이블·같은 RLS를 쓰므로 권한 설계를 새로 하지 않아도 된다.

## 4. 노출 정책 — 3단계

무엇을 보여줄지보다 **무엇을 절대 안 보여줄지**를 먼저 못 박는다.
경계가 흐릿하면 언젠가 화면 하나가 점수를 흘리고, 그 순간 플랫폼은 분쟁 무대가 된다.

### Tier 1 — 본인에게 항상 공개 (사실 기록)

다툼의 여지가 없는 "본인이 한 일"만 들어간다.
오히려 보여줘야 스스로 고친다.

- 프로필 완성도(P) 점수 + 비어 있는 항목과 채우는 방법
- 참여 이력: 지원 n건 / 확정 n건 / 완료 n건
- 출결 사실: 체크인 n회 / 노쇼 n회 / 지각 n회
- 일정 응답률

### Tier 2 — 관리자가 건별로 승인해야 공개 (성장 피드백)

- `visible_to_dancer = true` 로 표시한 평가의 **`shared_note` 텍스트만**
- 원 점수·축별 점수·평가자 신원은 **어떤 경우에도 포함하지 않는다**
- 기술적 보증: RLS는 컬럼 단위 제한이 안 되므로 전용 RPC `get_my_dancer_feedback()` 로만 내보낸다
  (반환 컬럼이 `project_title` / `shared_note` / `created_at` 뿐이라 점수가 물리적으로 새어 나갈 수 없다)

### Tier 3 — 내부 전용 (절대 비공개)

DQS, 등급·백분위, 축별 원점수, **재섭외 의향**, 평가자 신원, 원 코멘트, 클라이언트 결정(selected/hold/excluded).

재섭외 의향이 가장 민감하다.
"이 디렉터가 나를 다시 안 부르겠다고 했다"가 새는 순간 평가 제도 자체가 끝난다.

### 주체별 요약

| 대상 | 볼 수 있는 것 | 볼 수 없는 것 |
|---|---|---|
| 댄서 본인 | Tier 1 전부 + 관리자가 공개한 Tier 2 코멘트 | DQS·등급·축별 점수·재섭외 의향·평가자 |
| 프로젝트 담당자 | 담당 프로젝트 지원자의 평가·코멘트 (기존 RLS) | 타 프로젝트 평가, 종합 DQS |
| 현장 매니저 | 본인이 배정된 이벤트 참여자의 운영 지표 | 디렉터·클라이언트 평가 원문 |
| 외부 클라이언트 | 본인이 입력한 리뷰만 | 그 외 전부 |
| deetz 관리자 | 전부 (DQS·등급·평가자·이력) | — |

## 5. 리스크와 가드레일

| 리스크 | 대응 |
|---|---|
| 점수 유출 → 분쟁·이탈 | admin-only RLS + 공개 RPC는 점수 미반환(기존 원칙 승계) |
| 소수 평가로 낙인 | shrinkage(k=3) + n<2 등급 미부여 |
| 특정 디렉터의 감정 평가 | 평가자 캘리브레이션 + 코멘트 필수(저점 시) + 관리자 리뷰 큐 |
| 신인 진입 불리 | 신규 6개월간 노출 부스트 슬롯 별도 배정 |
| 개인정보·명예 이슈 | 평가는 업무 수행 사실 기반으로만 작성, 외모·사생활 항목 금지 |
| 이의제기 | 댄서 문의 → 관리자가 근거 로그 확인 → 필요 시 개별 평가 무효화 |

## 7. 대표 결정 필요 사항

1. **마이그레이션 적용** — `20260814_001_evaluation_multi_role.sql` 을 운영 DB에 적용할지.
   BU DB 스키마 변경이라 승인 게이트에 걸려 있다.
   `alter column drop not null` 과 유니크 제약 교체가 포함된다(데이터 삭제는 없음).
2. **일괄 승인 실행** — A등급 169명(동명 충돌 제외)을 지금 승인할지.
   화면은 준비됐고, 버튼을 누르는 것만 남았다.
3. **승인 알림톡** — 현재 의도적 OFF라 승인해도 댄서는 모른다.
   켜면 폰 보유자에게 대량 발송되므로 별도 결정이 필요하다.
4. **재섭외 의향 노출 범위** — 관리자 화면에서 "재섭외 의향 3/4"를 캐스팅 시 바로 보여줄지.

**결정됨**: 평가 주체는 현장 매니저·디렉터·클라이언트 3종 (2026-08-14 대표 지시).
